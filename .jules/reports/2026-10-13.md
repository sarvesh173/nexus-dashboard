# Sentinel Audit Report — 2026-10-13

## Findings Summary

### Finding 1: Unhandled Non-200 HTTP Responses and Top-Level JSON Array Payloads in Model Catalog Sync
- **Severity**: Medium
- **Confidence**: High
- **Type**: Bug / Reliability
- **Location**: `run_sync.py:73`, `server.py:944`, `model_health.py:63`
- **Description**:
  When `run_sync.fetch_specs()`, `server.get_hermes_config_providers()`, or `model_health.live_catalog()` fall back to querying the provider `/models` endpoint directly using `requests.get()`, they assumed the response was an HTTP 200 with a dictionary structure (`{"data": [...]}`).
  1. If the endpoint returned a non-200 status (e.g. 500, 401, 429), `.json().get('data', [])` was called on error HTML/JSON, or yielded empty/unexpected structures.
  2. If the provider API returned a top-level JSON array (`[...]`), `.get()` raised an `AttributeError: 'list' object has no attribute 'get'`.
  3. If items inside the list were non-dicts or contained non-string IDs, `.get('id')` raised `AttributeError` or passed invalid IDs down to categorisation.

- **Impact**:
  An upstream HTTP error or non-standard payload shape in the fallback path resulted in unhandled exceptions or incomplete spec lists, disrupting model health probes and provider listings.

- **Fix Applied**:
  - In `run_sync.py`: Added explicit status code check (`r.status_code == 200`), handled both top-level list and `{"data": [...]}` dictionary structures, and skipped non-dict or non-string model entries.
  - In `server.py`: Safely unpacked `raw_json` as list or dict before iterating, skipping invalid entries.
  - In `model_health.py`: Handled list vs dict JSON payloads cleanly when extracting model ID sets.
  - Added unit tests in `tests/test_audit_fixes.py`.

- **Verification**:
  All 26 tests in `tests/test_audit_fixes.py` pass.
