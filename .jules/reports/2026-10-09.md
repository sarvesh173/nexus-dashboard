# Sentinel Finding Report — 2026-10-09

## Summary
In `omniroute_logs.py`, query parameter filtering (`model`, `provider`, `account`, `status`, `agent`, `search`) was performed in Python memory on a pre-paginated array returned by `read_call_logs(limit, offset)` instead of in the underlying SQLite queries.

## Evidence
`omniroute_logs.py`: `read_call_logs_page(qs)` previously fetched an unfiltered page of size `limit` at `offset` using `read_call_logs(limit, offset)`, and then filtered that small subset in Python:
```python
payload = read_call_logs(limit, offset)
calls = payload.get("calls") or []
...
if model:
    rows = [r for r in rows if r["model"] == model or r["requestedModel"] == model]
```
When query string parameters (e.g., `?model=openrouter/anthropic/claude`) were provided, any matches outside the first `limit` rows of the raw table were ignored, returning 0 rows or incomplete results and breaking offset pagination.

## Impact
- Filtered log queries in the dashboard logger view silently omitted matching records unless they happened to fall in the current unfiltered page window.
- Pagination controls displayed incorrect page numbers and totals when filters were active.

## Fix
Refactored `omniroute_logs.py` (`read_call_logs`, `_query_calls`, `_build_where`) to apply `model`, `provider`, `account`, `status`, `agent`, and `search` conditions directly in parameterized SQLite queries (`SELECT ... WHERE ... LIMIT ? OFFSET ?` and `SELECT COUNT(*) WHERE ...`). Keyed the TTL list cache on the active filter tuple.

## Confidence & Severity
- **Confidence**: High
- **Severity**: High
