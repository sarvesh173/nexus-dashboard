# Sentinel Audit Report - 2026-10-09

## Summary
Discovered a query parameter filtering bug in `omniroute_logs.py` where filtering parameters (`model`, `provider`, `account`, `status`, `agent`, `search`) are applied in Python memory AFTER executing SQLite pagination via `LIMIT` and `OFFSET`.

## Finding Details
- **File & Line**: `omniroute_logs.py:619-644`
- **Issue Type**: BUG / PERFORMANCE / RELIABILITY
- **Severity**: Medium
- **Confidence**: High

### Description
In `omniroute_logs.py`, `read_call_logs_page(qs)` handles request parameters for the call log viewer.
It executes `payload = read_call_logs(limit, offset)` which runs `SELECT ... FROM call_logs ORDER BY timestamp DESC, id DESC LIMIT ? OFFSET ?` directly against SQLite.
After fetching this fixed-size slice of rows, `read_call_logs_page` filters `rows` in Python memory using list comprehensions for parameters such as `model`, `provider`, `account`, `status`, `agent`, and `search`.

If a user filters by `model=gpt-4` and requests `limit=50&offset=0`, SQLite fetches the 50 most recent call logs across ALL models. If none of those 50 call logs match `gpt-4`, Python memory filtering drops all 50 records and returns an empty list `[]`, despite thousands of matching `gpt-4` records existing in the database. Furthermore, offset pagination (`offset=50`) is offset against unfiltered total records rather than matching records.

### Impact
Call log filtering by model, provider, account, status, agent, or search yields empty or incomplete result pages and breaks pagination for filtered queries on large database stores.

### Suggested Fix
Refactor `_query_calls` and `read_call_logs` in `omniroute_logs.py` to build a dynamic SQL `WHERE` clause for filtered parameters (`model`, `provider`, `account`, `status`, `agent`), executing filtering directly within SQLite prior to `ORDER BY`, `LIMIT`, and `OFFSET`.
